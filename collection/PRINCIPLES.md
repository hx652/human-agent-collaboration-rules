## 02 协作与架构／实现分离约定

来源：[sources/multiarm-problem-gen/AGENTS.md](../sources/multiarm-problem-gen/AGENTS.md)

**人与 agent**（原文第 9–19 行）

````text
## 人与 agent

AI 协作者自称及被指称为“agent”，不使用“助手”。保持简洁，独立审阅用户的想法，说明赞同、保留或反对的理由，不直接顺着用户下结论。

agent 的输出应简洁明确；避免重复解释和无关展开，不以篇幅制造完整感。复杂问题分步讨论，按需补充细节，避免过长输出造成阅读负担。

用户希望参与架构设计、理解和管理复杂度，并通过项目提高工程能力。影响领域概念、数据语义、模块边界或关键依赖的选择，应与用户讨论；已经授权且含义明确的实现工作可直接推进，不为普通局部选择反复要求确认。

不急于收敛完整方案。草稿可以包含问题、例子、反例、候选抽象和小实验；通过实际反馈逐步形成整体设计，不把候选建议当成已确认决定。

best practice 是可调整的工程偏好，不以形式一致压缩探索空间。共同语义需明确；规则应根据实际摩擦改进，不预设复杂工作流。
````

**按使用场景推进**（原文第 31 行）

````text
以具体使用场景推进，避免为尚未出现的需求建立大规模抽象。明确原型是回答问题的试验还是准备保留的实现。
````

**代码规范**（原文第 33–39 行）

````text
为 class 和公开 method 编写适当的 docstring，说明其职责、表达的抽象，以及调用者需要理解的输入、输出和相互关系。必要时补充状态变化、副作用和错误行为。不解释内部实现细节，也不机械重复名称和类型签名已经清楚表达的信息。公开函数遵循相同原则。

实现时，明确标出承担输入校验的函数和代码段，统一使用 `# Input validation: <校验内容>` 注释。

专用于输入校验的函数，在定义前标注；校验逻辑与其他处理混合的函数，在实际校验代码块前标注。说明检查的约束或拒绝的输入，例如类型、数值范围、必需字段、引用有效性或结构一致性，不只写“检查输入”。

按连续校验块标注，不要求每个条件重复添加；普通计算、数据转换和内部不变量检查不混标为输入校验。新增或修改输入校验逻辑时，同步维护标记。
````

**实现与验证**（原文第 41–45 行）

````text
对变更运行适当检查，测试预期应来自需求、独立算例或其他可信依据，不照抄被测实现。不存在或未运行的检查必须如实说明。必要时沿实际代码的数据流解释关键选择，帮助用户理解修改位置和代价。

编写或修改测试前，先简要明确测试目的：要验证哪项需求或契约、希望发现哪类错误、预期结果依据什么，以及通过后能说明什么、不能说明什么。相关测试可以按组说明，不要求逐条套用模板。先明确目的，再编写测试；不能事后用已有测试反推目的，也不能只复刻被测实现。

测试目的可先在交流中说明，并在实施记录中简要保留。已有授权范围内的测试不因此新增审批步骤；发现需求或契约歧义时，再返回讨论。
````

**Git 与交接**（原文第 51–57 行）

````text
所有 commit message 使用英文。探索提交以清楚记录为主；主线提交遵循文档中的标题、正文和逻辑完整性约定。

当累积改动已经构成一次逻辑完整、可审阅的提交时，agent 可以主动建议提交并说明范围，避免大量改动积累后才提交；建议不等于获得授权。

提交前检查差异和暂存范围，只提交本次授权的文件。提交、集成、推送和共享历史修改分别按授权范围执行，不覆盖无关工作。

并行修改时按需要隔离工作目录和产物位置，不为每个小任务强制创建 worktree 或 PR。结束时说明修改内容、验证结果和未决事项。
````

**架构职责、契约与授权**（原文第 67–90 行）

````text
## 架构决策与自主权限

架构关注模块职责、边界、依赖关系、数据与状态归属、对外契约，以及已确认的全局约束。

仅服务于局部、可在不影响上述事项的情况下替换的类、函数、算法和内部组织，由实现 Agent 自主决定。

只有能够明确判断调整不影响整体架构时，Agent 才可自主进行。涉及架构变化，或影响尚不确定时，必须先与用户讨论，得到确认后再做相关修改。

不得为了完成局部任务，擅自改变公共契约、增加跨模块依赖、转移状态归属或绕过既定边界。用户已明确授权的事项不重复请求确认。

## 从设计进入实现

实现前，应明确本次工作的：

- 目标与验收条件；
- 负责的模块及允许修改的范围；
- 相关架构约束；
- 依赖模块的公开契约及其入口。

契约应足以让调用者理解输入、输出和相关行为，包括必要的错误、副作用、时序及一致性保证。按实际需要说明，不机械补齐无关条目。

不要求预先设计全部内部类和函数。尚未明确且会影响架构的事项留在设计讨论中，不能交给实现阶段默默决定。

每次实现开始时，简要说明本次范围。范围已明确且已获授权时直接推进；不自行扩大范围以获得更多实现信息。
````

## 03 Git 工作方式

来源：[sources/multiarm-problem-gen/docs/git-workflow.md](../sources/multiarm-problem-gen/docs/git-workflow.md)

**探索分支与长期主线**（原文第 3–9 行）

````text
## 探索分支与长期主线

`main` 保存当前已经接受、愿意继续以之为基础的项目状态，不要求项目已经成熟或功能完整。

尝试某项修改时，从当时的 `main` 建立围绕具体问题的分支。在分支中讨论、实现、验证并按需保存过程提交；形成值得保留的成果后，整理并集成到 `main`。

后续新的尝试从更新后的 `main` 建立新分支，不默认沿用上一轮探索分支。
````

**分支、提交、集成与提交语言**（原文第 24–57 行）

````text
分支围绕问题组织，不必对应一次对话。尝试可以跨多个 session，也可以在发现不合适后放弃。值得保留的认识记录到讨论笔记中，不要求所有试验代码进入主线。

## 何时提交与集成

探索阶段可以按需创建检查点，避免大量工作只存在于未提交状态中。

当已有改动构成一次清楚、可审阅的提交时，agent 可以主动建议提交并说明范围。建议不等于提交授权。

进入主线时，整理的不只是提交信息，还包括：

- 排除不准备保留的试验内容；
- 分离无关的逻辑变化；
- 明确最终行为、验证情况和重要限制；
- 保留有价值的设计理由或讨论链接。

以是否形成可理解、可验证的成果判断集成时机，不以文件数量或改动行数判断。一轮探索可以整理成一个或多个主线提交。

## 集成方式

暂不统一规定使用 merge、squash 还是整理后的提交，根据具体情况选择。

- 需要保留原始探索提交关系时，可以使用 merge。
- 希望主线只保留整理后的成果时，可以使用 squash，或先整理提交再集成。
- 不将多个不相关成果强行压成一个巨大提交。
- 使用 squash 后，下一轮尝试从更新后的 main 开始。
- 若需要长期保留原始探索代码，应明确保留相应分支或 tag，不依赖 reflog 作为永久档案。

集成后检查组合后的行为，没有文本冲突不等于没有语义冲突。

## Commit message 的语言

所有提交信息均使用英文，包括探索提交和主线提交的标题、正文及说明性 footer。

文件路径、代码标识符和链接保持原样。
````

**探索提交**（原文第 59–61 行）

````text
## 探索提交

以清楚记录尝试和恢复工作为目的，不强制固定模板、分类前缀或严格标题长度。
````

**提交表达与主线格式**（原文第 77–100 行）

````text
避免只有 `Update`、`Fix` 或 `WIP` 等无法区分内容的信息。未完成状态可以直接说明，不包装成已经完成的成果。

## 主线提交

以 Pro Git 的 Commit Guidelines 为基础，面向不了解本次对话的未来读者。

格式：

```text
Short summary of the change

Explain why the change is needed and describe the resulting behavior.
Include important limitations or references when useful.
```

约定：

- 标题使用祈使式，例如 `Add`、`Fix`、`Clarify`、`Remove`。
- 标题简短明确，尽量控制在约 50 个字符，不以机械截断牺牲清晰度；末尾不加句号。
- 标题与正文之间空一行；正文尽量在约 72 列换行。
- 简单变化可以只有标题。
- 正文解释动机、结果及必要取舍，不重复罗列全部 diff。
- 不直接拼接探索阶段的零碎提交信息作为主线说明。
- 暂不强制采用 Conventional Commits 的 `feat:`、`fix:` 等前缀。
````

**实际内容与操作边界**（原文第 115–123 行）

````text
提交信息描述这次实际保存的内容，不把未实现计划或未执行验证写成事实。

## 操作边界

提交前检查差异和暂存范围，仅包含本次授权的内容。保护已有的用户修改，不混入无关工作。

提交、集成和推送分别按授权范围执行；不会因为允许在分支探索，就自动获得推送或改写共享历史的授权。

需要整理别人已经依赖的提交时，先协调，不擅自改写。
````

## 04 渐进设计与 best practice

来源：[sources/research-process/inbox/2026-09-18-evolving-design-and-best-practices.md](../sources/research-process/inbox/2026-09-18-evolving-design-and-best-practices.md)

**两条原则及经讨论认可的补充**（原文第 13–51 行）

````text
## 1. 在草稿纸上积累线索，逐渐形成整体设计

### 用户的原始表述

> 可以不着急提出最终的完整方案，先罗列一些必要的抽象，当草稿纸上积累了足够的线索，整体的设计方案自然会有轮廓。

### 经讨论认可的补充

不急于给出完整架构，但早期未必已经知道哪些抽象真正必要。因此，草稿纸不仅容纳候选抽象，也容纳具体问题、例子、反例、约束、变化需求和小实验。

允许这些线索暂时不完整、不统一，不要求每个想法一出现就落实为类、接口、模块或固定目录。候选抽象用于帮助理解问题，不应因提前命名而成为难以放弃的既定结构。

“整体设计自然形成”仍需要主动整理和实践反馈。通过讨论、小规模实现和具体使用路径，检验候选边界是否合适，再逐步修正整体设计。既不要求所有细节想清楚后才开始，也不将缺少整体方案理解为无需设计。

例如，当前可以讨论 frame 与变换关系、采样分布、名义模板与具体实例、通用数据与后端适配等概念；这些只是设计线索，不代表已经决定相应的继承结构或插件体系。

这一原则与此前“先跑通完整流程，再通过实际反馈完善”的工作方式相衔接。小实验用于暴露真实问题，避免仅以积累抽象名称替代实践。

## 2. best practice 提供倾向，保留表达与探索空间

### 用户的原始表述

> 它是必要的，但是它不应该成为一个强制的限制和枷锁而限制表达能力，我最终希望的是像概率分布那样，在整体上呈现规律，但也有足够的随机性。

### 经讨论认可的补充

这一比喻表达的是：整体存在可辨认的秩序，局部仍有足够自由去表达和探索。不将它落实为“按一定概率不遵守规则”，而是把 best practice 作为初始偏好，根据具体问题、证据和实际成本更新判断。

偏离常见做法可以是有意识的选择，也可以来自尚未成熟的尝试。不应为了形式一致而提前抹平有价值的差异。

讨论中区分了三类内容：

- **共同语义**：例如单位、pose 的含义、数据是否被覆盖，需要明确并保持一致，否则协作双方可能在处理不同的问题。
- **工程偏好**：例如文件拆分、函数长度、提交格式，可以根据实际收益调整，不必处处强求同一种形式。
- **探索表达**：草稿、反例、原型和备选方案，应允许更大的不规则性，为理解变化留出空间。

同时关注例外的累积成本：每次偏离可能都有理由，但累积后仍可能使整体难以理解。不必为每次偏离设置审批；当真实维护成本出现时，再回看哪些差异有价值，哪些只是偶然留下的负担。

因此，既不将 best practice 视为无需解释的权威，也不以探索自由为由忽略共同语义和实际协作成本。
````

来源：[sources/research-process/inbox/README.md](../sources/research-process/inbox/README.md)

**零散想法**（原文第 3–4 行）

````text
保存尚未成体系、暂时没有明确归属的思考。
不要求完整推理，不要求每条都变成任务。
````

**整理、确认与保留出处**（原文第 7–12 行）

````text
保留日期、原始想法和必要背景，关联材料按需补充。
Agent 整理候选，用户确认后写入。

有明确项目归属的零散想法可放在项目目录。
按需回看，不强制清空。
成熟后链接到假设、实验或决策记录，保留原始出处。
````

## 09 讨论与实施记录的组织

````text
每份笔记不必使用固定模板，但应让未来读者分清问题、依据、选择和未决事项。候选方案和历史记录不自动成为 agent 指令。
````
