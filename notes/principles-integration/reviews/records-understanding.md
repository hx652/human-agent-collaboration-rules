## 对记录原则的理解

记录服务于理解问题及其演变。记录范围可以包括探索、设计、实施、排查、实验和复盘；三类示例既不是穷尽分类，也不规定各类的固定结构。取舍以内容对理解与脉络的作用为依据，要保留初始问题、发展、选择与结果形成所需的信息。影响理解的依据、分歧、错误、失败尝试和转折不能因压缩而消失；重复且没有新增信息的表达可合并，无关操作细节可省略。

表达应清晰、简洁、易读、易懂，结构和详略由实际内容决定。整理或压缩不得补出没有发生的过程，要区分用户与 agent 的表述，也要区分猜想、候选、未决事项和已确认结论。可靠的现有资料可引用或定位，以免重复维护无关、易过时状态；若当时状态影响判断，则仍需留下相关事实及其影响。

记录按主题、用途和关系组织，遵从仓库现有结构，使用反映内容的目录及文件名，并按需建立引用。agent 应持续留意进展，在已有内容足够形成有意义的记录时主动建议；若已有明确记录要求，直接按要求执行。正文并未把“建议记录”写成一律自动生成记录。

原意审查核查整理稿是否忠实于原始材料，只是完整审查可能包含的一部分。整理用户与 agent 交流时默认启用并告知用户；完全由 agent 生成、不是整理双方交流的材料则仅默认提出审查建议。原始材料优先来自本地 session，按需提取并保留出处；来源不完整需说明局限，并补充可核实材料，不能用可获得原文的摘要替代原文。

启用原意审查时要使用 subagent 独立比较由原始材料和整理结果分别形成的理解，检查影响理解的遗漏、变化和无依据补充。两个隔离上下文分别只读原文或整理稿、各自先保存理解，再由独立审查者比对和回查，是可采用的一种流程，配置应随规模和重要性选择。原文阅读者的理解也需核验，合理压缩的详略差异可以接受。

## 读取入口及组合关系

`README.md` 介绍五份正式文件，要求先了解通用原则，再按场景读取专题；向其他仓库整合时，以正式正文和用户确认的采用范围为准。整合流程要求完整阅读全部专题，确认适配范围，合并重复内容，设置直接的专题读取指引，并整体检查遗漏、冲突、边界和链接。原始材料、筛选记录、实验档案和 README 不默认整合。

`RULES.md:11` 是记录专题的实际读取入口：整理、维护或审查讨论与工作记录前主动阅读。通用原则的简洁表达、范围约束、按需取证和信息隔离继续约束记录行为；`RULES.md:55` 保留主动建议记录的基本要求，与 `RECORDS.md:35` 相同。两处重复可理解为入口保留基本要求、专题完整呈现细则，并无语义冲突。

`CODE.md:71` 对实现、审查和编写测试明确要求过程记录，并转到记录原则决定内容取舍。测试记录另有具体重点：用例形成、正确性依据、取舍，而非逐次运行流水账（73 行）。这与“重要错误和失败要保留”相容：影响分析或调整的结果按需保留，不要求记录所有无关结果。

`GIT.md` 要求保留有价值的选择理由和探索认识，排除不保留的试验代码；记录承接这些认识，不等于所有探索代码或检查点必须进入主线。提交组织按目的和逻辑关系，不因记录跨文件就机械拆分。记录建议和提交建议是不同活动，且提出提交方案不产生执行授权。

`SERENA.md` 规定代码信息的定向获取与边界控制；`CODE.md:9` 已明确过程记录、摘要和转述同样不能绕过隔离。记录原则没有扩大获取信息的权限。本地 session 取证仍受通用原则的信息隔离要求约束，原意审查要求独立判断，不能因取证而将不允许的信息带入受限上下文。
