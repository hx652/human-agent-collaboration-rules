## 代码原则的理解

正文按七个主题组织：基本原则；两种视角与信息隔离；公开约定与文档；避免过度工程化；判断与验证；工具使用；过程记录。

基本目的在于降低理解和修改代码的认知负担，使职责、依赖、协作和抽象清楚。设计从具体问题和反馈逐步形成，不要求一开始定下完整架构。既定设计和授权范围内的局部决定可自主处理；改变职责、模块关系或对外约定的架构调整，要先讨论并由用户确定，已有授权无需再确认。

全局视角允许在获准范围内跨抽象边界了解实现、调用和状态，从而理解真实行为和因果；不要求读完全部仓库。受限视角依照当前设计层级、职责、任务允许的信息判断，且可以通过公开抽象理解整体架构。实现负责部分时可按边界读取该部分实现；使用依赖部分只可读取公开抽象与对外约定。公开约定不足应指出缺口和影响、返回设计讨论，不能自行补语义或由缺口直接断言内部结构有问题。

信息边界先于任务分配与上下文划分：边界可细至类、函数或方法，同一文件不能因此一起读取；扩大负责范围或合并任务不能放宽边界。同一上下文可承担多个任务，但该上下文已有、获取、产生和接收的全部信息，必须同时符合各任务的边界。已经接触禁用信息的上下文不具备承担相关受限任务的资格；先后执行或声称忽略信息无效。搜索、引用、诊断、测试输出和过程记录也受相同约束。

架构审查要求有独立的受限判断，并由不同上下文取得全局参考。受限审查先关注整体职责、能力边界、依赖及协作；全局参考说明事实与推断。在独立受限判断形成并保存之前，参考及摘要不能进入该上下文。之后由主 agent 对照两份结果，检查差异，也检查全局参考是否有问题；之后的复核不能再称独立受限审查。

测试编写或修改要求上下文不含被测部分实现信息，也不得间接取得它。可以运行真实被测代码及依赖、观察公开行为。测试从需求、公开抽象及允许的调用信息形成，先简述目的、可能发现的问题和正确性依据。不得照抄实现或未经核对把当前输出当答案。重点是实际重要场景、真实边界及公开失败约定，避免缺少依据的极端组合。检查报告要承认局限；不能通过削弱约定、删除有效测试或让调用者适配内部缺陷造出通过。

问题追踪使用全局视角查实际行为和发生路径；修复转为受限视角，依据职责与对外约定判断局部问题或整体设计问题。依照前文的一般资格规则，我理解为：追踪中一旦接触到修复任务禁止的信息，该上下文不能再承担该受限修复；跨上下文交接也不能带入被禁止的实现信息。正文未在问题追踪小节另行规定交接格式。

公开类、方法、函数须有说明抽象及调用所需行为的文档，按需包含副作用和失败行为，不展开实现或重复已清楚的信息。输入校验按连续块解释所检查约束，与普通计算和内部不变量区分。文档和类型标注随改动维护，不顺带补无关代码。

复杂度控制要求满足当前需求的简单方案，保留必要功能、边界和验证；抽象、包装、通用化、配置、兼容和防御逻辑都要有实际收益或需求。审查者的偏好和无依据风险不能自动增加结构或验证负担。架构可通过少量现实变化情境评估理解、修改和连带影响；这些情境不自动成为新需求或扩展点。

代码信息获取和修改须按边界使用 Serena；不可用时暂停相关操作、由用户决定。过程记录按记录原则执行；测试记录保留形成过程、正确性依据和取舍，不逐次抄运行结果；只清理本次新增且不再需要的临时产物，保留交付及有价值记录。

## 组合规则关系

`RULES.md` 是通用入口，规定代码、Git、记录和 Serena 的读取时机，并提供判断范围、简洁表达、信息隔离及 subagent 的共同要求。其隔离规则适用于所有明确设边界的任务；`CODE.md` 对代码职责、依赖使用、测试与架构审查给出更具体的边界。

通用 subagent 原则鼓励主动分工和互补视角，同时要求背景按职责及信息需要安排、审查已有历史、保留自主判断，并告知用户配置。代码中的上下文资格约束进一步限定这些分工：提供背景不能越过任务边界，全局参考不能提前污染受限判断。

`SERENA.md` 把代码隔离落实为查询范围和返回内容注意事项；激活项目不等于获得所有信息权限，查询参数也不是强制访问隔离。工具看不到信息不等于设计缺信息，无法安全控制范围时改读明确允许的公开材料。代码正文和指南各有一次不可用处理说明，语义一致。

`RECORDS.md` 要求记录有助于理解的脉络、依据、错误和取舍，区分用户与 agent、保留确认状态，并允许合理压缩。原意审查默认用于双方交流的整理，由独立 subagent 对照理解和原文核验；完全由 agent 生成的材料只建议审查。代码过程记录因此不应变成固定模板或堆积运行日志，也不能为了记录而跨越信息边界。

`GIT.md` 单独规定操作授权、逻辑提交及集成检查。提出方案不等于执行授权；提交、集成、推送各按授权范围执行。最终组合还需检查语义，不能只看文本无冲突。

README 将 `rules/` 正文与确认采用范围作为当前可用规则，要求整合前了解项目、向用户报告内容与取舍并确认、整合后检查。notes 只作历史讨论索引，当时的待定状态不直接决定当前规则状态。
