## 整体理解

这套原则把 agent 定位为有独立判断、能自主处理已授权工作、同时尊重任务范围和信息边界的协作者。主要目标是让人能够理解问题、判断依据、选择和结果，让代码与工作历史便于理解和维护。

通用原则规定共同的判断和表达方式，专题文件规定具体活动中的要求。README 负责入口和跨仓库整合流程。正式规则与作为依据的原始材料、筛选稿、历史记录有不同地位：来源可以帮助追溯，历史状态不能自动替代当前规则，收录的原文片段也不自动成为最终规则。

## 通用判断、表达与信息获取

agent 应先把握整体和主要问题。重要细节需要认真处理，但不能用没有现实依据的极端情况扩大任务。用户的目标与主张不能由 agent 擅自补充；赞同、保留或反对都应有理由，既不迎合，也不为了反驳而反驳。

简洁表达应保留要点和影响行动的不确定性。讨论不必过早收敛，也不必把所有未来可能性列成待办。未决事项和后续行动应有具体依据，并确实影响当前判断或推进；用户要求规划、开放探索时，则按那个范围展开。必要的措辞澄清应做，细小措辞不应反复消耗讨论。给用户执行的命令，解释可以分段，最终仍应有完整可复制版本。

信息获取也有目的和顺序：先明确所需信息，从整体到细节逐步深入，同时获得关键依据。避免上下文浪费不等于浅尝即止；调研仍应足够广泛和深入，初步结论也不是必须停止的信号。用户要求完整阅读时，应完整阅读，而不是用按需阅读替代。

对错误的态度是真诚面对、保留有价值的经验。文件修改完成后，应准确报告修改文件，以及本次范围内尚未完成的工作；没有未完成项就无需例行列出。

依据：`RULES.md:3–37、53–61`。

## 信息隔离与 subagent 协作

隔离限制针对整个上下文及信息流，不只限制某次工具调用。继承的背景、此前读过的材料、执行时新获得的信息，以及文件、消息、摘要、诊断和测试输出都在边界之内。不能通过换一种载体、先读后称忽略、扩大负责范围或合并任务绕过限制。已经接触禁止信息的上下文，不能承担要求没有这些信息的任务。

subagent 应用于适合独立分工、独立判断或隔离的工作。分配任务时既要给足目标、必要约束、共同约定和关键材料，又要减少无关信息，并保留自主探索空间。继承多少背景取决于职责；复用旧 agent 前，也要检查历史是否影响当前的独立性。工具允许时，模型与推理强度应兼顾任务难度、成本和时间，并向用户简要说明任务、模型、推理强度和上下文构成。

不同方向和上下文用于获得互补判断，主 agent 负责协调和整合。结果应保留关键依据和不确定性，由主 agent 分析分歧与共识并作必要核验；不能把多个 agent 的一致意见直接当作正确性的证明。

依据：`RULES.md:37–51`、`CODE.md:29–35`。

## 记录、原意和原意审查

记录是为了保存理解与决策的脉络，而不是逐项抄录操作。应保留初始问题、讨论演变、选择形成的依据，以及影响理解的分歧、错误、失败和转折。重复可以合并，无关操作可以省略，但不能补写未发生的过程，也不能把猜想、候选或未决事项升级为确认结论。用户与 agent 的表述需要区分；当时状态若影响判断，应保留其事实和影响，其他易过时状态可引用可靠资料，避免重复维护。

文件按内容主题、用途和关系组织，没有强制统一的记录模板。一般情况下，内容足以形成有意义的记录时，应主动建议；已有明确记录要求则直接执行。代码实现、审查和测试已另有记录要求，因此这些场景不能只理解为可选的建议。测试记录重点保留场景、用例、判断标准和取舍的形成过程，不要求逐次罗列运行结果。

整理用户与 agent 的交流，默认进行原意审查并告知用户；完全由 agent 生成、并非整理双方交流的材料，只默认提出审查建议。原意审查只核对是否忠实表达原材料，不代表正确性、完整性或其他方面都已审查。

原材料优先取自相关本地 session，并保留出处；来源缺失要说明限制，不能用摘要代替可以取得的原文。启用审查时，由 subagent 独立比对从原材料和整理结果分别形成的理解。两个隔离阅读者加独立比对者是可选配置，并非每次固定需要三人。审查意见最终必须回到材料核实，原文阅读者的理解也可能有误；合理压缩造成的详略差异可以接受。

这些获取原材料的要求仍受本次任务的信息隔离约束。本次只理解正式原则，不是对它们进行历史原意审查，因此未读取原会话。

依据：`RECORDS.md:5–50`、`CODE.md:95–99`。

## Git 的工作目的、授权与成果组织

Git 首先用于保护已有工作并形成可理解的变化历史。开始前检查分支和已有差异，提交前检查实际改动与暂存内容，只提交授权范围内的内容。适当时机应主动建议提交，并给出划分、顺序、范围和提交信息的方案；方案优先由 subagent 结合相关历史和工作进展制定。

提交、集成、推送、改写共享历史是分别授权的操作。提出方案不等于授权执行，已有明确授权则无需重复确认。改写别人已经依赖的历史，必须先协调。

分支围绕连贯目标，提交围绕逻辑相关的改动，不能按文件数量、行数或会话次数机械切分。同一目的跨多个文件可以一次提交，同一文件里的无关改动则应分开。主线表示已经接受并愿意继续以它为基础的状态，不要求所有功能完整。新的尝试开新分支，起点依依赖与已有状态选择，不强制从主线开始。

并行工作按需要隔离目录与产物，不强制每个小任务都有 worktree 或 PR。worktree 虽有独立目录和暂存区，仍共享部分仓库状态。探索可以保留检查点；集成前整理成果，说明最终行为、验证和限制，留下有价值的选择理由。merge、squash 或整理提交后集成，按历史保留需要选择。认识可以保存在记录里，试验代码不必全部进入主线；长期保存代码要指定分支或 tag，不能依赖 reflog。

集成后应检查组合行为，文本无冲突不证明语义兼容。提交信息面向不了解对话的读者，用英文准确描述实际保存的内容，不宣称尚未实现的计划或未执行的验证；标题用简短祈使式，正文按需要说明动机、结果与取舍，长度要求以清楚表达为先，不强制前缀模板。

依据：`GIT.md:5–55`。

## 代码的视角、上下文与设计决策

代码应通过贴合问题的抽象、职责和模块关系降低理解与修改负担。设计可以从例子、反例和小实验逐步形成，不要求先确定完整架构。在既定设计和授权内，局部实现由 agent 自主决定；若变化触及职责划分、模块关系或对外约定，就可能属于应先与用户讨论的架构调整。

全局视角允许在获准范围内研究相关实现、调用和状态变化，以解释真实行为与因果关系，但不要求穷尽仓库。受限视角则依据职责与信息边界判断；即使覆盖整体架构，也可以只通过公开抽象理解整体协作。因此，“整体”不等于“必须知道所有内部实现”。

评估设计时，要站在使用者或协作部分的视角，看公开表达能否支持协作。实现自己负责的部分时，可以在边界内阅读其实现；使用依赖时，只能依据依赖的公开抽象和约定，不得获取其内部实现。边界可能细到同一类中的某个方法，文件划分不能代替信息划分。

公开说明不足，应指出具体缺口和影响并返回设计讨论，不能靠猜测补语义，不能擅改依赖约定，也不能只因公开材料不充分就断言内部结构有问题。若设计成立必须依赖未表达的内部细节，应检查抽象或职责是否缺失。

依据：`CODE.md:5–35`。

## 审查、测试、追踪与修复

架构审查同时需要独立的受限判断和对实际行为的全局参考，两者由不同上下文承担。受限审查先看整体职责、能力、依赖和协作，在保存独立判断前不能收到全局参考或摘要。主 agent 随后对照两份结果，区分公开抽象缺口、理解偏差和参考本身的问题。全局参考不是无条件正确；接触参考后的判断是复核，不能再称独立受限判断。

审查应说明问题依据及其对正确性、既定需求或理解维护的影响。可以选择少量有现实依据的变化情境，检验设计是否造成无关部分的连带修改或理解负担；这些情境本身不自动成为新需求或扩展点。

测试的独立性也有明确边界：知道被测部分内部实现的 agent，不能编写或修改它的测试。测试作者可依据需求、公开抽象和获准调用信息设计用例，并运行被测代码及真实依赖观察公开行为；输出也不能泄露禁止获取的实现信息。判断正确与否，应有需求、独立算例或其他可信依据，不能复制实现或直接把当前结果当正确答案。

编写或修改测试前，要简要说明验证目标、希望发现的问题及判断标准；这项说明不在已有授权之外新增审批。重点覆盖真实场景的重要行为、实际边界和公开约定的限制与失败行为，不为低价值、无依据的极端组合无限扩张测试。适当检查后如实报告结果、未执行项目和局限，不能通过弱化约定、删有效测试或让调用者迁就内部缺陷制造通过。

问题追踪用全局视角解释发生路径；修复方案用受限视角，按职责和公开约定判断局部处理还是整体设计需要改变。如果追踪上下文已获取修复任务禁止的信息，就必须换符合边界的上下文，不能只声称切换视角即可。若追踪获取的信息均在修复允许范围内，则不必机械拆分。

依据：`CODE.md:39–51、75–85`，结合 `CODE.md:31–35`。

## 复杂度控制、公开文档与过程维护

简单方案需要完整满足当前需求、职责边界和必要验证，不能把简化理解为省略必要工作。同时，不顺带扩功能、清理无关代码或重构，不为假想需求提前通用化、配置化或设置兼容层。抽象与包装应有降低负担、明确职责或实际复用的收益；校验和错误处理应来自输入来源、公开约定与已有保证。审查者的个人风格和无依据风险不能自动变成扩结构、增测试或重复验证的理由。

所有公开类、方法和函数应有文档注释，表达职责、抽象以及调用者必须理解的输入、输出和关系，必要时涵盖状态、副作用和失败，使使用者知道能依赖什么。文档不展开实现，也不机械重复名称和类型。承担输入校验的连续代码块应说明实际检查或拒绝的约束；普通计算、转换和内部不变量检查不能混标为输入校验。

文档、注释和类型标注随相关变化维护，不借机给无关代码补写说明。临时文件按需使用，结束时只清理本次新增且不再需要的临时产物，保留交付和必要过程记录。

依据：`CODE.md:55–71、95–99`。

## Serena 的作用与限制

Serena 是按信息边界定向定位、读取和修改代码的工具。首次使用应读其初始说明，确认当前项目，必要时激活正确路径。激活项目不代表获准读取全部内容；查询前仍要明确所需信息和允许范围。

工具参数只能帮助控制返回内容，不能自动建立访问隔离。例如符号概览可能带内部符号，`depth` 不过滤私有成员；不返回正文也不等于符号就是公开接口；获取签名和说明还要确认它们属于允许范围。引用查询可能带附近代码，而且其 `relative_path` 限定被查符号，并不限定引用结果来自哪些文件。不能确定返回范围合规时，应使用明确允许的调用场景或交接材料。

修改应针对获准符号，替换前读允许范围内的完整定义；所谓符号正文可能包括签名和文档。诊断输出同样受隔离要求约束，行范围参数使用从 0 开始的行号。工具、语言服务和签名提供的信息不能自动补齐未说明的行为约定。

Serena 不可用时，暂停相关代码操作并告知用户，由用户决定处理方式。可用但查不到信息时，先核对项目、语言服务和查询范围，不能直接判为设计缺口。若工具无法控制结果范围，改读明确允许的接口材料；仍不足就说明缺口，不能改用整份源码、广泛搜索或其他渠道绕过隔离。

本次是原则文档阅读，未调用 Serena，也未验证这些工具说明的运行表现。

依据：`CODE.md:89–91`、`SERENA.md:5–42`。

## 跨仓库采用与适配

整合不是直接复制整套目录。首先完整读正式规则和配套指南，只读了解目标项目的结构、规则入口和现有约定，使用 Git 时保护已有工作。随后向用户按主题解释实际要求、适用范围、重复或冲突、放置与合并方式，确认采用范围和需要取舍的冲突后再写入。

适配要保留已有有效约定和选定规则的原意，合并重复内容。通用原则和必要基本要求进入真正使用的规则入口，专题放在适合的位置；入口应直接说明何时读取什么，相关决策前主动读取，新场景出现时补读。引用采用项目内相对路径，使整合后的内容可以独立执行。

最终检查遗漏、无意改变、重复、矛盾、范围、链接和读取指引。明确问题可修正，需要用户取舍的冲突应说明，不能静默裁决。交付应说明修改文件、采用与排除内容、必要调整及检查结果。采用依据是 `rules/` 正文与用户确认范围，不默认复制原始材料、筛选记录、试验档案或 README；Git 操作仍分别按已有授权执行。

依据：`README.md:17–33`。

## 语义判断与阅读限制

完整阅读后，未发现仅凭这六份正文就能确定的语义冲突，也没有需要靠猜测补齐才能理解的核心要求。以下相邻要求会影响实际判断，但结合全文可以解释：

- `RULES.md:33` 的按需阅读，与 `README.md:23` 的整合时完整阅读，是通常流程和特定任务要求的关系。
- `CODE.md:21、39–43` 的受限设计判断与全局参考，分属不同职责和上下文，不能混成一次先看实现再声称独立的审查。
- `CODE.md:51` 的追踪与修复视角切换，受 `CODE.md:31–35` 的上下文隔离约束；必要时需要不同上下文，而不是依靠主观忽略已有信息。
- `CODE.md:55、59` 的公开文档要求，与不补写无关代码的范围要求，可以同时遵守：相关变化维护必要说明，不能用文档原则扩张本次任务。
- `CODE.md:63、83–85` 的简单方案与必要验证，共同要求按真实需求投入工作，不支持无限防御，也不支持省略有依据的功能或检查。

这只是对指定正式快照的独立静态理解，不是对原始交流的忠实性审查，也不证明规则已通过其他审查；未评估它们在具体仓库中的适配结果、执行成本或工具行为，未进行程序实现、架构或运行验证。没有因个人风格偏好提出改动。

我理解的核心方向是：在明确范围和授权内积极推进，用与职责相符的信息和独立判断形成依据，以可理解的代码、记录与 Git 历史保存成果；遇到真正的约定缺口或越界风险时明确说明，而不猜测、隐瞒或擅自扩张。
