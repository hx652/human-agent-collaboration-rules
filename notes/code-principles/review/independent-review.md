## 明确且可直接修正的问题

### D1：受限视角的总定义容易把设计阶段限制泛化到负责实现本身

**位置**：`notes/code-principles/topic-reorganization-draft.md:21-23`；相关归纳说明位于 `topic-reorganization-plan.md:43`。

**依据**：A15 的受限视角解释及 U09 的基本认可；原始摘录 A15 第 260–263 行、U09 第 282–284 行，session 源行 293、301。既有 `rules/CODE.md:35` 是设计阶段的公开抽象要求，`:41` 则允许读取本次负责范围内的实现。

**问题及影响**：重组稿第 21 行作为一般性的“受限视角”定义，写成“仅依据各部分对外表达的职责、能力和约束”“不依赖各部分的内部实现细节”。这些措辞原先服务于设计判断，移到总定义后，容易被理解为受限修复或实现也不能依赖自己负责部分的实现，与第 23 行允许按边界读取负责实现，以及 A15 的明确例子形成歧义。用户认可的是依赖信息受限、边界随层级与职责确定的理解。

**修正方向**：总定义以“当前层级、职责和任务允许依赖的信息”为依据，把只能依据公开抽象的限制落在依赖或其他受限部分上；保留第 23 行“在既定信息边界内”的前提。不要反过来写成所有受限任务都能读取负责实现，测试等任务仍应服从各自边界。这是消除重组造成的适用范围歧义，不增加新的权限或流程。

### D2：完整预览没有完整对应追踪与修复的专项候选约束

**位置**：`notes/code-principles/topic-reorganization-draft.md:49-51`；对应 `problem-tracing-and-fix-draft.md:5-9`；相关状态说明位于 `topic-reorganization-plan.md:45`、`README.md:147-149,159-161`。

**依据**：U06（源行 237）、U07（源行 251）、U11（源行 448）提出追踪与修复原则并要求草稿；A25（源行 494，原始摘录第 435–442 行）给出三段专项草稿，并说明同步到完整预览。讨论记录第 147 行正确标明额外衔接内容属于 agent 补充，仍待核对。

**问题及影响**：专项草稿明确要求对追踪所得认识区分已验证事实与推断；完整预览第 51 行没有这一点。预览第 41 行的事实与推断要求只修饰架构审查的全局参考，不能明确覆盖问题追踪。专项中的公开信息缺口、返回设计讨论及信息隔离要求，在预览第 25、13、29–35 行已有相关一般表达，不必重复所有内容；但至少上述追踪判断依据没有明确落点。记录虽说明总览简述、专项展开，预览仍自称完整正文，并没有指向专项作为该节的完整候选内容，交给整合者时可能形成两种不同的采用结果。

**修正方向**：统一两份候选文本的含义，至少让完整预览明确保留追踪中的事实与推断区分；或明确说明专项如何构成完整候选正文，并调整“完整预览／同步”的说明。继续标为候选，不将 agent 的补充升级为用户已确认要求。这里的问题是候选成果的同步和交付含义，不是断言用户明确提出过每项补充，也不要求机械重复条文。
