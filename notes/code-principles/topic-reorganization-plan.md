# 代码原则按主题重组方案

本方案以现有[代码相关原则](../../rules/CODE.md)的正文为依据归纳主题，再结合本次讨论形成[完整预览](topic-reorganization-draft.md)。当前仅保存方案和草稿，正式规则尚未修改。

## 从现有正文归纳的主题

正文包含五个主体主题，以及工具使用、过程记录两项配套主题。用户先前提出的基本原则、两种视角与信息隔离、避免过度工程化均在其中；另外两项值得单独表达的是公开约定与文档、判断与验证。

| 主题 | 现有内容 | 归类理由 |
|---|---|---|
| 基本原则 | 易于理解和维护、清晰的职责和依赖、通过例子与反馈形成设计、局部决定与架构调整的权限。 | 规定代码工作的目标、设计形成方式和决策边界。 |
| 两种视角与信息隔离 | 公开抽象、依赖实现的读取限制、上下文分工、受限架构审查、全局参考与独立判断、测试上下文隔离。 | 规定判断能依赖什么信息，以及如何维持这一边界。 |
| 公开约定与文档 | 公开接口必须说明的内容、输入校验注释、文档与类型标注的维护。 | 规定代码需要表达哪些信息，使职责、行为和约束可理解。 |
| 避免过度工程化 | 改动范围、抽象与封装、假想扩展、必要校验和错误处理，以及无依据的审查意见不能推动复杂度增长。 | 控制实现和维护的复杂度，使投入有实际需求和收益。 |
| 判断与验证 | 审查依据、用真实变化评估架构、测试场景和独立判断标准、验证范围及结论的限度。 | 规定判断与结论的依据，覆盖审查、测试和结果报告。 |
| 工具使用 | 按边界使用 Serena、按需读取、工具不可用时的处理。 | 保留具体工具要求，操作细节继续由 Serena 指南承载。 |
| 过程记录 | 工作记录、测试形成过程、临时产物的保留与清理。 | 保留代码工作中的记录要求，并衔接独立的记录原则。 |

公开约定与文档关注应当表达什么，信息隔离关注能够获取什么，判断与验证关注依据是否足以支持结论。三者有关联，但分别成节更容易找到相应要求。

## 建议结构

完整预览按上表顺序组织。原来的设计、实现、审查和测试场景按其具体含义归入主题；在信息隔离主题内部，保留独立判断、测试隔离、问题追踪与修复等应用说明。

“两种视角与信息隔离”包含：视角与判断依据、上下文划分与信息传递、独立判断与全局参考、测试中的信息隔离、问题追踪与修复。这里保留的是各场景中的原则和约束，不另设固定执行流程。

## 原有条文的归属

| 原章节 | 重组后的归属 |
|---|---|
| 工具使用与信息边界 | 信息隔离要求进入“两种视角与信息隔离”；Serena 要求进入“工具使用”。 |
| 避免过度工程化 | 范围与复杂度要求保留；文档维护进入“公开约定与文档”；审查依据进入“判断与验证”；临时产物要求进入“过程记录”。 |
| 设计 | 目标、架构清晰和设计探索进入“基本原则”；依据公开抽象推演及识别缺口进入“两种视角与信息隔离”。 |
| 实现 | 上下文与依赖使用进入“两种视角与信息隔离”；局部决定与架构调整权限进入“基本原则”；文档和校验注释进入“公开约定与文档”。 |
| 审查 | 受限判断、全局参考及二者对照进入“两种视角与信息隔离”；可维护性评估与真实变化推演进入“判断与验证”。 |
| 测试 | 上下文和运行输出的隔离进入“两种视角与信息隔离”；场景、判断标准、检查与结果报告进入“判断与验证”。 |
| 过程记录 | 保留在“过程记录”，继续引用独立的记录原则。 |

重组保留现有实质要求；拆分同时涉及多个主题的段落，合并重复表达，并删除“公开接口文档和输入校验注释按实现部分执行”这类因原章节归属变化而失效的指引。

## 本次讨论带来的补充

- **集中说明两种视角**：将用户已评价为“基本没有问题”的理解写成主题开头，说明全局视角与受限视角的区别和用途。这是对原有分散表述的归纳与补充。
- **补强上下文划分**：纳入上一轮[上下文划分草稿](context-isolation-draft.md)的三段内容；同时为“负责范围内可以读取实现”明确加上“在既定信息边界内”的前提。
- **补充问题追踪与修复**：根据用户描述形成[专项草稿](problem-tracing-and-fix-draft.md)。完整预览的对应段落保留两种视角及追踪中事实与推断的区分；公开信息缺口、设计调整及全过程隔离等要求归并在同一预览的通用条文中，专项草稿集中展开这些含义。它们是供核对的候选内容，不当作用户已经逐项确认的要求。
- **明确全局视角的应用**：架构审查和问题追踪使用全局视角，以直接陈述表达要求。架构审查中的全局参考与受限判断保持上下文隔离，并在受限判断独立形成后进行对照；相应删除“可由另一个 agent”“如有全局参考”等可选表述。

## 拟修改的正式文件

- 代码相关原则：按完整预览重组正文，采用时将指南链接调整为正式文件所在位置的相对路径。
- 仓库 README：同步更新代码原则的一行简介，建议为“清晰易维护的代码、两种视角与信息隔离、公开约定、适度复杂度、判断与验证，以及工具和记录要求。”

通用原则中按设计、实现、审查、测试场景触发读取代码原则的指引仍然适用。工具的具体使用方式继续由 Serena 指南说明，记录的一般要求继续引用记录原则。
