## 讨论与核查

### 实现时的信息隔离粒度

**agent：现有表述的核查**

[实现部分](../recording-principles/integration-review/round1/rules/CODE.md#实现)要求“根据当前设计层级的信息边界安排负责范围和上下文”，并区分本次负责部分与依赖部分。这些表述没有将文件规定为划分单位，可以容纳类、函数或方法级的边界，但没有直接说明这种粒度，也没有明确指出同一文件或同一类中可以存在不同的信息边界。

[Serena 使用指南](../../rules/SERENA.md#定位与读取)已经写明“不要为查看一个方法而读取整个类的正文”，体现了方法级读取的要求。因此，现有规则方向一致，值得补充的是实现任务和上下文的划分粒度。

**agent：补充方向，尚未确认**

根据实际的信息隔离需要确定负责范围和上下文，粒度可以细到类、函数或方法。同一文件或同一类中的其他实现，也应遵守已确定的信息边界；不能因共同所在的文件或类而自动扩大可读取范围。是否拆分上下文取决于隔离需要，不机械要求每个方法都使用单独上下文。

### 按主题组织代码原则

**agent：对整理方向的理解与建议**

现有结构将同一套信息隔离思想分散在设计、实现、审查和测试中，读者需要跨章节拼合其整体含义。按主题组织，可以先说明原则及其理由，再集中说明它在不同工作中的应用。

根据用户目前的表述，初步理解为三条主线：

- **基本原则**：代码清晰易读、方便维护，降低理解和修改的负担。
- **两种视角与信息隔离**：说明两种视角及由此推导的信息隔离要求，集中组织其在设计、实现、审查和测试中的应用。前面讨论的类、函数和方法级边界属于这一主题。
- **避免过度工程化**：围绕当前需求选择简单方案，使抽象、封装、扩展、校验和验证具有实际依据。

设计、实现、审查和测试仍可作为主题内部的应用场景，按需帮助组织内容。重组时还需核对现有具体要求的归属，包括公开接口文档、输入校验注释、授权边界、工具使用、验证与过程记录，保留其原意。以上是组织方向的初步理解，具体标题和条文安排尚未确定。

### 问题追踪与修复中的两种视角

**agent：原则层面的理解，待继续讨论**

全局视角帮助理解程序的实际行为及问题发生的路径。评估修复方案时，应在受限视角下，从程序各部分的职责和对外约定出发理解问题的成因，判断是局部处理不足，还是整体设计存在问题，并据此提出修改方案。这一补充可归入“两种视角与信息隔离”主题。

两种视角在这里各有作用：全局理解提供对实际行为的认识，受限视角为判断修复的合理性提供依据。对于“程序的视角”，agent 当前理解为各部分依据自身职责以及能够依赖的公开约定理解和协作。

**agent：根据用户澄清调整整理方式**

后续整理应突出原则的含义、依据和适用范围。用户提到的 IDE 逐步跳转、调用链等具体做法，是帮助理解全局视角的例子；保留这些例子所表达的意图，不将其直接改写为固定操作流程。

### 对全局视角与受限视角的当前理解

**agent：依据本次描述和现有规则形成的理解，供用户核对**

**全局视角**：可以跨越程序各部分的抽象边界，按需了解相关内部实现、实际调用和状态变化，形成对真实行为及其因果关系的认识。这里的“全局”表示能够贯通相关部分的信息，并不要求穷尽整个仓库。

**受限视角**：在当前设计层级和职责范围内，以允许依赖的信息理解和判断程序。对其他协作部分，依据其公开的职责、能力和约束推演行为，不用未公开的内部实现补全理由。具体边界随任务确定；例如实现某部分时，可以理解负责范围内的实现，而对依赖部分依据公开约定使用。边界可以细到类或方法。

两种视角的区别在于判断可以依赖哪些信息。受限视角也可以覆盖整体架构，通过各部分的公开抽象理解整体协作；“受限”不等于只能看局部。agent 将其理解为实际的信息边界：不能将超出边界的实现知识作为受限判断的依据。

结合问题追踪与修复，全局理解有助于认识问题实际怎样发生；受限判断关注各部分能否依据自身职责和公开约定正确协作，并据此评估局部处理或整体设计的修改是否合理。以上尚待用户核对，未作为对原始材料的还原。

**后续反馈**：用户随后评价“你的理解基本没有问题”。保留上文当时的理解及核对状态，原始材料尚未重新核查。

### 上下文划分中的隔离约束

**agent：核查结果**

现有规则已经要求需要隔离的实现由不同上下文处理，不因合并任务放宽信息边界；还禁止先读取受限信息再声称忽略。因此，合起来理解时，没有明确允许违反隔离要求的条款。

仍有值得补强的表述：

- “本次负责范围内的实现可以按需阅读”必须服从既定的信息边界。若先将需要隔离的实现合并为负责范围，再据此扩大可读信息，就违背了原有要求；应直接写清信息边界约束任务分配。
- 原文以“当前设计层级”描述粒度，但没有明确说明边界可以细到同一文件或类中的不同实现。文件或类的归属不能替代信息边界。
- 通用规则已经要求检查已有上下文的信息，代码规则还可直接说明其对任务分配的后果：已经包含受限信息的上下文不能承担相应任务，任务改为先后执行也不会消除这个冲突。

**agent：草稿与适用范围**

[依据信息隔离划分上下文草稿](context-isolation-draft.md)将这些要求集中表达为持续约束，允许满足隔离要求的任务共用上下文，并明确不能借任务合并扩大信息边界。草稿拟归入“两种视角与信息隔离”主题，尚未写入正式规则。后续采用时，“本次负责范围内的实现可以按需阅读”等表述应与这一前提保持一致。
