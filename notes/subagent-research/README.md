# Subagent 上下文与自主委派调研

调研日期：2026-10-12。状态：供共同讨论，尚未形成正式原则。

起点是[用户提出的观点](../2026-10-12-subagent-principles.md)。三位 `gpt-6.1-sol / max` subagent 分别研究官方机制、工程实践和实验证据；主 agent 综合并复核关键来源。[调研安排](arrangement.md)保留分工与信息边界，[来源索引](sources.md)保留日期、证据性质和定位。

本轮材料支持把上下文安排看作 Subagent 的重要价值：按任务分配信息、隔离探索过程，并让主 agent 汇总。更完整的设计还应保留必要的共同事实、安排信息补取和证据回传。社区已有自主委派的实现，但委派能力、稳定收益和最优决策属于不同层次的结论。

## 与用户观点的对照

| 用户观点 | 本轮调研后的判断 |
|---|---|
| 最大优势是上下文的重新划分和安排 | 是有明确实践依据的重要优势；本轮证据没有给上下文管理、并行速度、专业工具和额外计算作统一排序，暂不能把“最大”作为普遍事实。 |
| 先明确任务所需信息，再划分上下文 | 与当前做法一致。还应考虑任务进行中发现的新信息、跨任务依赖及结果怎样返回，允许调整划分。 |
| 不同上下文类似不同视角，结合后可以改善决策 | 是合理方向，但需要互补的证据、候选或检验方法。新会话、不同角色名及意见一致，都不能单独证明视角质量。 |
| 提供知识和合适引导后，可让 agent 自主决定 Subagent 的使用 | 已有提示驱动和专门训练的实现。应同时教会它何时值得委派、怎样传信息、怎样验收，以及何时结束或调整。 |

这些是主 agent 对下述来源的综合判断，不是用户已接受的新规则。

## 上下文包含什么

需要区分模型当前实际接收的内容，与可通过文件、检索或工具取得的材料。当前输入可能包括指令、任务、被传入的历史、工具描述、工具结果及检索片段；材料存在于磁盘或程序状态中，并不表示模型已经读到。OpenAI SDK 明确区分程序的 run context 与模型上下文。[OpenAI Agent definitions](https://developers.openai.com/api/docs/guides/agents/define-agents)

“新上下文”通常也有平台指令和工具配置；它是否继承主会话、自动加载项目规则或保留历史，取决于具体实现。上下文分离与文件、工具权限应分别判断。[OpenAI Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents)、[Claude Code subagents](https://code.claude.com/docs/en/sub-agents)

## 如何划分

LangChain 在 2026-09 的说明中明确区分独立上下文与完整 fork，并根据工作性质选择。下面的第三列是结合本轮材料提出的讨论建议，不是所有产品的默认行为。[Organizing Context in a Multi-Agent Harness](https://www.langchain.com/blog/organizing-context-in-a-multi-agent-harness)

| 工作性质 | 常见上下文安排 | 需要保留的信息 |
|---|---|---|
| 独立研究一个问题 | 新上下文，接收任务和必要材料 | 研究问题、范围、日期或版本、来源要求和输出目标 |
| 独立审查 | 新上下文，提供被审对象和判断依据 | 需求、公开约定和相关证据；审查者先形成判断，再对照提出者的解释 |
| 承接已有工作 | 相关历史交接，必要时完整 fork | 已确认决定、约束、现状和重要失败尝试，避免重复发现或违背前序决定 |
| 持续跟踪同一问题 | 延续既有子会话，并更新任务 | 仍然有效的状态与证据；检查旧假设是否过时 |
| 强依赖、频繁修改同一状态 | 保留共同决策，明确修改和整合责任，必要时串行处理 | 跨任务约束和会影响其他部分的变更 |

完整继承可以减少背景重建，也会带入原有假设。独立输入可以减少锚定和无关过程，也可能漏掉必要决定。因此，“需要什么信息”与“需要独立于什么判断”应一起考虑。Cognition 2026 年的复盘同时采用独立审查和较完整背景的专家咨询，说明两种选择各有用途。[Cognition 实践更新](https://cognition.com/blog/multi-agents-working)

## 成功经验与具体问题

**并行研究可以扩大信息覆盖。** Anthropic 的研究系统由主 agent 动态规划，子 agent 分方向检索并压缩回传。作者报告内部评测提升 90.2%，但比较同时涉及模型组合、搜索和计算投入，未提供同预算的上下文隔离消融。其约 15 倍 token 数的比较对象是普通聊天，不是该评测中的单 agent。可借鉴的是清楚的分工、回传及按复杂度分配努力，不能照搬收益比例。[Anthropic 复盘](https://www.anthropic.com/engineering/multi-agent-research-system)

**上下文筛选有较直接的同模型实验。** LangChain 使用 gpt-4o，在 100 个零售任务中增加无关领域的工具和规则。干扰较多时，划分后的系统优于装入全部材料的单 agent；干扰较少时，单 agent 仍略优。该任务几乎不需要跨 agent 协调，不能推广为复杂协作的普遍优势。[LangChain 基准](https://www.langchain.com/blog/benchmarking-multi-agent-architectures)

**共享文件不能代替协作设计。** Cursor 的长期编码实验从同级 agent 共享文件和锁，改为 planner、worker、judge 分工，报告了吞吐与协调方面的改善。但模型、提示和计算投入也在变化，大量代码或 CI 通过不等于完整产品验收。[Cursor 编码复盘](https://cursor.com/blog/scaling-agents)

**回传通道本身可能丢信息。** deepagents 的 issue 中，维护者确认一种实现只提取子 agent 最终消息的文本，会丢失非文本内容；讨论建议分别保存模型可读摘要和程序需要的完整材料。这是具体实现的问题，也提醒我们检查证据是否真的到达接收者。[deepagents #2512](https://github.com/langchain-ai/deepagents/issues/2512)

## 多个上下文怎样成为有效视角

需要分别评价上下文是否独立、内容是否不同，以及这些差异是否带来互补的正确信息。同模型 agent 可能共享知识缺口；不同任务也可能重复检索相同来源。结合结果时，应比较证据与理由，而非把人数或一致意见当成可靠性证明。

研究结果并不支持一种固定的交流政策。2025 年的《Debate or Vote》发现，在其同质小模型答题设置中，独立投票解释了多数收益，辩论未稳定超过它。2026-10 的《When Debate Helps》则通过互补候选和证据核验，让交流获得额外收益。后者是新近预印本，且两者主要测试可判定答案的推理题；不能直接等同于开放研究或仓库协作。[Debate or Vote](https://arxiv.org/html/2508.17536v2)、[When Debate Helps](https://arxiv.org/html/2610.04686v1)

对本仓库的合理启发是：需要独立判断时，先保留各自结果；之后允许带着可核查证据交流、比较和修正。共享哪些信息及何时共享，应服务于判断目的。这是设计推断，尚未在本仓库做对照验证。

## 由 agent 自主决定怎样使用 Subagent

这已不只是设想。Anthropic 的系统用提示指导主 agent 分解问题、创建子 agent 并判断是否继续。Kimi K2.5 的技术报告则描述通过专门训练学习动态数量、职责和调度；其并行时间收益不能视作相同总计算下的上下文隔离收益。[Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)、[Kimi K2.5 v2](https://arxiv.org/html/2602.02276v2)

从这些实践归纳，提供给主 agent 的知识和引导可以覆盖以下内容，具体详略随任务调整：

- 能调用什么能力，各类 subagent 适合什么工作，实际怎样传入和回传上下文。
- 当前工作能否独立分解，共享哪些决定；预期收益来自覆盖、独立核验、专业能力还是并行执行。
- 每个任务的目标、信息入口、操作范围和完成标准；信息不足时怎样请求补充。
- 怎样核对关键结果，以及何时停止、缩减、继续调查或改变分工；与已有授权及资源约束保持一致。

这不是要求用户为每次委派制定详细方案，也不是固定提示模板。主 agent 可以在已有任务范围内运用这些知识作判断，并根据反馈修正。

但“能自主选择”不代表“选择可靠”。Cognition 的专家咨询实验中，较弱主模型在何时求助、如何提问上成为瓶颈；Claude Code 的社区 issue 也报告过范围模糊、漏传决定和不核验结果。后者为未独立复现的用户经验，其因无活动关闭也不代表问题已修复。[Cognition 实践更新](https://cognition.com/blog/multi-agents-working)、[Claude Code #40339](https://github.com/anthropics/claude-code/issues/40339)

## 证据边界

官方文档说明能力与建议，工程复盘提供情境经验，论文提供特定设置下的比较，它们承担的证据作用不同。NoLiMa 支持无关长度可能妨碍信息利用，但没有直接测试 Subagent；Scaling Agent Systems v3 的六类基准显示架构与任务依赖结构需要匹配，也未单独操纵上下文继承策略。[NoLiMa](https://arxiv.org/html/2502.05167v3)、[Scaling v3](https://arxiv.org/html/2512.08296v3)

本轮没有复现实验，也没有为 GPT-6.1-Sol / max 测量不同上下文策略的净收益。仍需保留的问题是：某项任务究竟应继承多少历史，怎样衡量视角互补，以及自主委派相对简单方案是否值得。它们不能靠来源数量或 subagent 之间的赞同来解决。
