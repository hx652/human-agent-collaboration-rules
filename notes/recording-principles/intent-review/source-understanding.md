这次工作的起点，是用户尚未形成清楚表述，先逐步保存想法，再共同整理（L73、L85）；当前交付要求则是形成简洁清晰的整体草案，单列未确定事项（L898）。因此，需要保留讨论中的修正和确认状态，不能把所有出现过的说明、建议都直接当成已定原则。

最重要的修正涉及“为什么记录”和“原则写什么”。长期保存 Session 中的理解、进展与上下文，以及支持跨 Session、多 agent 长期协作，最初用于解释记录的作用（L155）。用户先澄清协作是形成记录后的好处（L572），随后明确它只是意图说明，不应写进原则（L1027）；连“长期保存理解与进展、保留上下文”这句目的说明，也提出删去（L1056），并在 assistant 赞同后要求修改草案（L1063—L1070）。这些背景仍有助于理解意图，但不能因此重新写成原则正文。

场景按记录内容来分，而非按协作方式来分（L85）。用户希望把具体场景归成少数大类，认为想法探索和知识学习相近；又认为复盘与经验总结也接近想法或学习，无须独立列类（L401、L414）。assistant 据此提出“理解与探索、设计与决策、实践与验证”，并把复盘放入第一类（L411、L424、L564）。用户认为场景已经大致明确，但反对给每类场景套确定结构，理由是可能限制表达（L572）。分类名称与归并在此前仍被称为候选或倾向。

用户直接提出的核心要求，是记录呈现问题、想法、讨论过程、最终选择等完整脉络，同时清晰简洁、易于阅读（L187、L217）。对现有记录的不满，是有用信息夹杂大量次要细节，以及反复保存易过时、可另行核实又非核心的状态；Git 提交状态是其中的例子（L217）。用户认可根据“缺少什么会使脉络断裂、哪些细节无助于理解”进行取舍（L746、L753）。assistant 随后展开为保留必要脉络、详略匹配重要性、利用已有资料减少重复维护、保持原意与确认状态；包括保留关键分歧和转折、不把猜想写成结论，以及必要时保留影响判断的历史状态（L794）。这些展开是 assistant 的提议，用户以“好的”接续并补充审查（L801），材料没有逐项核定的记录。

审查的核心是用户提出的：比较整理结果带来的理解与原始材料带来的理解（L801）。两位读者分别只读一种材料，第三位在两份理解保存后比对、回查，两位读者得到相同目的与范围说明，三者采用新上下文，是 assistant 提出的具体方案；原始材料读者也可能误读，合理压缩造成的详略差异可以接受，意见须说明位置与影响，主 agent 再复核（L852）。用户最后明确要求按该方案审查当前草案，并优先读取本地 session 原始记录（L1070）。不能把完整三角色流程理解成用户已要求所有记录无差别采用：方案本身允许按影响范围简化（L852）。

另有两项直接要求：agent 留意进度，在足够形成记录时主动建议记录（L859）；文件按语义选择合适位置，方便检索查看（L966）。用户授权理解原意后补充表达，但当次只修改文件组织部分（L996）。主题、用途、相互关系、结合仓库结构、清楚命名和按需引用，是 assistant 随后的具体展开（L1020），此范围内未见用户再逐项评价。

建目录保存原始想法、使用 subagent 调研、先明确场景再讨论内容，以及本轮修改后审查，属于本次工作过程要求（L85、L304、L361、L1070）。调研应包括已有问题、可能成因、成功经验，以及记录之外的协作手段（L247、L280、L572）；“问题与模型特点有关”是用户判断，不能只凭这些对话认定已证实。调研摘要也不自动成为记录原则。

材料尚未明确“足够形成记录”的统一判断尺度；部分展开获得整体接续认可，但最终确认到何种粒度仍含糊。这里仅指出原始讨论的状态，不判断未知草案是否缺项。

实际读取来源：仅通过指定命令运行 extract_dialogue.py，读取指定本地 session 第 73—1070 行中经机械筛选的用户与 assistant 可见消息。未读取整版草案、其他文件、记忆、链接或其他 agent 输出；未发生信息边界越界。
