## 目标与产物形式

整理一份人与 agent 协作时的基础规则，作为其他仓库的起点。目标仓库可以选择、调整和整合这些内容，形成适合自身的协作约定。

以有版本管理的文件仓库为主体，提供规则模板和使用说明。现有 `sources/`、`collection/` 与实验档案保留原始依据，按需追溯，不要求每次任务全部读取。原项目已确认的约定，仍需判断是否适合推广到其他项目。

Skill 可在后续承载接入和更新流程，帮助 agent 分析目标仓库、识别冲突并完成整合；是否制作、何时制作尚未确定。

## 规则的组织与读取

用户提出的组织方式：`AGENTS.md` 包含通用原则，其他方面的规则放入独立文件；在 `AGENTS.md` 中记录位置，并提示遇到相关场景时读取。

整理时遵循以下方向：

- `AGENTS.md` 保持精简，包含通用原则、不可遗漏的基本要求和专题索引。
- 索引同时说明文件位置、适用场景和读取时机；在相关决策或操作前读取，任务过程中出现新场景时补读。
- 专题文件展开具体做法，尽量由入口直接指向，避免多层跳转和重复维护同一规则。
- 使用目标仓库内的相对路径，规则入口与专题文件一起迁移，并检查链接。
- 文件位置与约束程度分别说明：通用原则可以是可调整的偏好，专题规则也可以在特定场景下必须遵守。

专题文件依赖 agent 根据指引主动读取，普通 Markdown 链接本身不等于自动加载。不可遗漏的核心约束保留在入口中，详细做法再按需展开。

讨论中的目录示例为目标仓库中的 `AGENTS.md` 配合 `collaboration/`，专题曾举例为设计、实现、记录和 Git；这些名称和划分尚未确定，也不要求目标仓库照搬。

## 接入目标仓库的流程

用户明确提出三项要求：

1. 适应目标仓库的组织结构，同时保证链接位置正确。
2. 整合前向用户报告包含哪些内容，让用户决定排除哪些内容。
3. 整合结束后做整体检查，检查是否有相互矛盾的地方。

据此，整合流程按以下顺序组织：

1. **只读了解目标仓库。** 检查现有规则入口、相关文档及目录结构，识别已有约定和可能冲突。
2. **准备可审阅的整合方案。** 按内容主题列出拟引入的行为要求、适用范围、预期放置位置及合并方式，不只列文件名；需要用户取舍的冲突一并说明。
3. **由用户选择采用范围。** 用户决定排除或调整哪些内容，明确范围后再写入目标仓库。
4. **执行适配与合并。** 沿用目标仓库合适的组织方式，保留已有有效约定，合并重复内容，调整路径、链接和场景读取指引。
5. **检查最终结果并报告。** 修正路径错误和明确的重复问题，说明采用、排除、调整了哪些内容，以及检查范围和未解决项。

冲突检查在整合前后各进行一次：整合前帮助用户做取舍，整合后检查实际合并结果。检查范围包括链接和锚点是否有效、读取指引是否对应实际文件、同一场景下要求是否矛盾、通用与专题规则的适用范围是否清楚、原有约定是否被无意覆盖，以及候选建议或项目经验是否被扩大为普遍要求。

涉及协作方式或授权边界的实质冲突，不能静默替用户选择。链接检查可以自动化，语义一致性仍需审阅；结果应区分已解决的问题和仍需决定的问题。
