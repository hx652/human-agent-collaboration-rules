# 输入读取的实现单元划分

日期：2026-09-29

状态：整理此前提出的六单元方案，作为后续任务划分依据；不表示所有单元的接口和任务粒度已定稿。用户已选择单元 1 开始，当前进展见[首轮实现记录](../implementation/2026-09-29-first-implementation-results.md)，本文不重写为尚未开始。

## 划分方案

实现单元是可以独立交付和验收的任务范围，不要求对应一个 class、文件或 Python 包。

| 单元 | 内容与职责 | 依赖 |
|---|---|---|
| 1. 基础表示 | Pose、Frame、基本形状、Geometry、MeshResource；统一数值、几何和坐标关系，不读文件 | 无项目内依赖 |
| 2. 机器人表示与读取 | RobotModel、Link、Joint、公共配置；解析机器人配置与 URDF，关联内部结构并处理配置覆盖 | 1 |
| 3. 场景表示与读取 | Scene、Object、RobotInstance、场景规则；建立实例与 frame 关系，引用共享模型 | 1、2 |
| 4. 分布表示 | 多维均匀、高斯分布的参数与维度检查；不关联场景，本阶段不实现采样 | 无项目内依赖 |
| 5. Generation 表示与读取 | Generation、SamplingBinding；解析分布参数、命名中心、作用目标、分量映射及访问序列 | 2、3、4 |
| 6. 输入包读取与组织 | InputBundle、BundleReader；发现文件、组织读取、管理共享资源，检查跨文件关系并交付结果 | 1～5 |

机器人、场景等“表示与读取”放在同一单元，是一起交付的候选方案，代码职责仍然分开。若需要检验读取实现能否仅凭数据表示的公开契约完成，应拆成独立任务；详见[实现单元与代码职责的区别](2026-09-29-implementation-unit-and-responsibility.md)。

## 路径与共享资源的归属

单元 6 组织路径解析和共享资源管理，向模型、场景读取逻辑提供小型公开接口，用于解析相对路径、取得或复用资源。各读取部分不自行维护互不相通的全局缓存；MeshResource 的数据表示仍属于单元 1。

该接口及其最小实现需在单元 2 开始前准备，不能全部拖到最后。表中的依赖不代表单元 2、3 要读取 BundleReader 内部实现；它们仅使用事先定义的资源接口。具体接口尚待讨论。

## 运行时协作

```text
6 发现输入
  → 调用 3 读取 Scene
      → 遇到机器人配置，通过资源接口取得或复用 2 的读取结果
      → 使用 1 构建 frame、几何和实例关系
  → 调用 5 读取 Generation
      → 使用 4 构建分布
      → 关联 Scene 中已有的对象
  → 6 检查并交付 InputBundle
```

完整流程见[输入读取流程与对象协作](2026-09-28-input-reading-flow.md)。这里只划分读取和表示，不扩展到采样、场景生成或计算后端。

## 建议实现顺序

先从高层使用流程明确依赖契约，再按必要依赖实现：

```text
1、4 → 2 → 3 → 5 → 6 完整集成
```

其中 1 与 4 可独立安排，不要求同时实现；单元 6 的路径与共享接口需提前提供。Docker／Compose 环境作为实施基础，已另行安排，不强行纳入上述六个业务单元。

每项实现开始前明确公开契约、修改范围和验收条件；后续实现 agent 可执行真实依赖，但不阅读其内部实现。此划分不是要求一次性补齐所有内部类或方法，后续任务粒度应结合实际契约缺口调整。
