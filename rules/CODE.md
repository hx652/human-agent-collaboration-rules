# 代码相关原则

## 设计与抽象

代码应易于理解和维护，降低理解和修改所需的认知负担。贴合问题的抽象和模块结构，使人能够在适当层次理解行为、判断变化的影响并完成修改，而不必同时掌握大量内部实现细节。

抽象将实现细节放在边界内。使用者应能依据公开表达的职责、能力和约定理解与使用一个部分，而不必总是打开它的内部实现。

保持整体架构清晰、受控，关注职责划分、依赖关系和协作方式。局部实现不必逐一展开，但会影响架构选择或方案可行性的细节仍需研究。

设计可以从具体问题、例子、反例和小实验逐步形成，通过尝试与反馈检验假设、修正抽象；不必一开始就确定完整结构。

在既定设计和授权范围内，agent 自行决定局部实现细节。整体架构调整应先与用户讨论并由用户确定；已经明确授权的事项按授权执行，不重复确认。区分局部决定与架构调整时，关注改动是否影响既定职责划分、模块关系和对外约定。

## 两种视角

**全局视角**在获准范围内可以跨越相关抽象边界，按需了解内部实现、实际调用和状态变化，以理解程序的真实行为、因果关系和问题发生的路径。全局理解不要求穷尽整个仓库。

梳理仓库现状、整理归档或组织提交时，可以在获准范围内采用全局视角，了解相关文件、实现及其联系；其中涉及设计评估、代码实现或测试编写时，各自的信息边界仍然适用。

**受限视角**遵循现有的抽象层次和边界，严格约束能够获取的信息，从程序局部的视角看待整个过程。作为调用者，不查看被调用者的内部实现，只依据其公开表达的职责、能力和约定理解和使用它。受限视角也可以用于理解整体架构。

评估设计时，从当前层次的使用者或其他协作部分出发，仅依据各部分对外表达的职责、能力和约束理解结构、推演协作，不依赖内部实现细节。

实现本次负责的部分时，可以在既定边界内按需阅读该部分实现；使用依赖时，只依据其公开抽象和对外约定编写调用代码，不直接或间接获取依赖的内部实现信息。公开约定不足以支持必要使用时，说明具体缺口及影响，返回设计讨论，不凭猜测补充语义，也不擅自改变依赖的约定。

如果必须依赖未体现在抽象中的实现细节才能判断设计成立，应检查抽象或职责划分是否存在缺口。公开说明不足以支持判断时，指出具体缺口及影响，不据此直接断言内部结构有问题。

## 信息隔离与上下文

上下文划分和任务分配服从既定的信息边界。边界可以细到类、函数或方法；同一文件或类中的实现也按各自边界处理。不能通过扩大负责范围或合并任务放宽隔离要求。

同一上下文可以承担多个任务，前提是接触或产生的信息都符合各任务的边界。一个任务需要的信息若是另一个任务禁止获取的，应由不同且分别符合边界的上下文承担。

隔离覆盖上下文中已有的信息、任务中获取或产生的信息，以及上下文之间传递的信息。已经包含某项任务禁止获取的信息的上下文，不得承担该任务；先后执行任务或声称忽略已有信息，不能消除冲突。

对只允许了解公开抽象的部分，不得获取内部实现信息。引用、搜索、诊断、测试输出和过程记录同样受边界约束，不能通过源码片段、摘要或转述绕过隔离。

## 架构审查

架构审查中的受限判断应在独立上下文中进行，先从整体架构入手，关注职责划分、能力边界、依赖和协作关系，重点判断影响整体理解的结构问题，不必过度深入局部细节。

同时使用全局视角了解与审查相关的实际运行行为，形成全局参考，并区分已验证的事实与推断。全局参考与受限判断由不同上下文承担；全局参考及其摘要不得提前进入受限审查。

受限审查独立形成并保留判断后，主 agent 对照两份结果，分析差异来自公开抽象不足、理解偏差，还是全局参考自身的问题。全局参考不是无条件正确的标准；接触参考后的判断属于结合参考的复核，不能再称为独立的受限审查。

审查的重要目标是评估设计是否易于理解和维护。审查意见在既定边界内说明问题依据，以及对正确性、既定需求或理解维护的影响。

可以基于实际目标、使用场景或已有反馈，选择少量可能真实发生的变化，推演职责和协作关系受到的影响，评估理解变化、判断影响和完成调整所需的负担。关注架构层面的实质变化，以及不必要的连带修改或对原本无关部分的重新理解和重组。这些情境用于检验现有设计，不自动成为新需求、待办或预设扩展点的理由。

## 测试

含有被测部分内部实现信息的上下文，不得编写或修改该部分的测试；测试编写者也不得直接或间接获取这些信息。可以运行被测代码和真实依赖，观察公开行为，但运行输出仍受同一信息边界约束，不能带入源码片段或内部调用关系。

依据需求、公开抽象和允许获取的调用信息设计测试，结合被测部分如何被调用、接收什么输入以及调用者如何使用结果，形成场景和用例。

编写或修改测试前，简要说明要验证什么、希望发现哪类问题，以及如何判断结果正确。判断标准来自需求、独立算例或其他可信依据，不照抄被测实现，也不把未经核对的当前运行结果当作正确结果。相关测试可按组说明，无须逐条套模板；已有授权范围内不因此新增审批。依据缺失或约定含糊时，说明缺口并返回讨论。

测试重点围绕真实使用场景中的重要行为和可能出现的问题。实际场景会遇到的边界，以及公开约定明确的输入限制和失败行为，应纳入考虑；避免为缺乏场景或约定依据、价值很低的极端输入及组合扩张测试。

运行与改动相关的适当检查，如实报告结果、未执行的检查和验证局限，不把部分测试通过扩大为整体保证。不得通过削弱约定、删除有效测试或让调用者适配内部缺陷来制造通过结果；发现约定本身存在问题时，返回讨论。

## 问题追踪与修复

问题追踪时使用全局视角理解实际行为及问题发生的路径，区分已验证的事实与推断。修复时在受限视角下，依据各部分的职责和对外约定，评估问题源于局部处理还是整体设计，并据此提出修改方案。各阶段仍遵守相应的信息隔离要求。

## 公开说明与注释

公开接口的文档注释是抽象概念的延伸。所有公开类、方法和函数都应有文档注释，说明职责、表达的抽象，以及调用者需要理解的输入、输出和关系；必要时说明状态变化、副作用及失败行为，明确调用者可以依赖什么。

这些说明不展开内部实现，也不机械重复名称或类型签名已经清楚表达的信息。

对承担输入校验的函数和代码段，用注释说明检查的约束或拒绝的输入，例如格式、类型、范围、必需字段或引用有效性。按连续校验块标注，并随逻辑同步维护；普通计算、数据转换和内部不变量检查不混标为输入校验。

文档、注释和类型标注按既定规范随相关改动维护，不为无关代码补写或堆叠重复说明。

## 控制复杂度

选择满足当前需求、易于理解和维护的简单方案。只做本次任务明确要求或确有必要的改动，遵守既定设计与授权边界；不顺带增加功能、清理无关代码或重构，也不省略必要功能、职责边界和验证。

抽象和封装应能明确职责、降低理解负担或满足实际复用需要。一次性操作通常不必另设辅助函数、工具类或包装层，不增加没有实际收益的调用层次。

不为假想需求提前通用化、增加配置或扩展点。功能开关和兼容层应有实际的切换、迁移或兼容需求。

依据输入来源、公开约定和已有保证设置必要的校验及错误处理，不为缺乏依据的情形堆叠校验、回退和防御分支。审查者的风格偏好和缺乏依据的风险，不自动成为增加结构、扩张测试或重复验证的理由。

## 工具与记录

需要遵循抽象边界读取、讲解或修改代码时，使用 Serena 辅助定位并获取允许的信息。讲解代码时，可以围绕当前层次的职责、能力、约束和协作关系展开；讲解调用时，说明被调用部分提供什么能力、如何使用以及有哪些约束。

采用全局视角梳理现状、归档或组织提交时，可根据实际需要选择文件阅读、搜索和 Git 等工具；需要定位结构、引用关系或追踪路径时，也可使用 Serena。工具选择不改变信息边界。具体使用见 [Serena 使用指南](SERENA.md)。

实现、审查和编写测试时，按 [记录原则](RECORDS.md)记录工作过程。测试记录重点说明场景和用例如何形成、如何判断结果正确，以及编写和修改中的取舍；不要求逐次记录运行结果，与问题分析或测试调整有关的结果按需保留。

按需使用临时脚本和文件；结束时清理本次新增且不再需要的临时产物，保留必要的交付内容和过程记录。
