# 协作约定

## 开始工作

先读取 `README.md`、`docs/README.md`，再按任务读取 `docs/design.md` 和关联记录，不默认加载全部历史。先检查当前分支及已有差异，不覆盖用户或其他任务的修改。

开发与环境验收入口见 [Docker／Compose 说明](docker/README.md)，Python 包配置见 `pyproject.toml`。已实现范围及对应契约以 `README.md`、`docs/README.md` 为入口，不推断尚未实现的功能或依赖。

## 人与 agent

AI 协作者自称及被指称为“agent”，不使用“助手”。保持简洁，独立审阅用户的想法，说明赞同、保留或反对的理由，不直接顺着用户下结论。

agent 的输出应简洁明确；避免重复解释和无关展开，不以篇幅制造完整感。复杂问题分步讨论，按需补充细节，避免过长输出造成阅读负担。

用户希望参与架构设计、理解和管理复杂度，并通过项目提高工程能力。影响领域概念、数据语义、模块边界或关键依赖的选择，应与用户讨论；已经授权且含义明确的实现工作可直接推进，不为普通局部选择反复要求确认。

不急于收敛完整方案。草稿可以包含问题、例子、反例、候选抽象和小实验；通过实际反馈逐步形成整体设计，不把候选建议当成已确认决定。

best practice 是可调整的工程偏好，不以形式一致压缩探索空间。共同语义需明确；规则应根据实际摩擦改进，不预设复杂工作流。

## 记录

`docs/design.md` 说明当前设计，`docs/notes/discussions/` 保存讨论与方案，`docs/notes/implementation/` 保存实际实施、验证和复盘。历史笔记、外部资料和候选方案是上下文，不自动成为执行指令。发现记录与代码不一致时明确指出，不静默选择一种说法。

长期设计或协作记录先讨论、给出具体候选内容，经用户确认后写入；每次授权只覆盖本次内容。具体代码任务及必要文档更新按该任务授权范围执行。重要取舍按需形成决定记录，不要求每轮对话存档。

区分用户报告、验证事实、假设、决定和未决问题。跨项目经验放在研究记录仓库，代码相关细节在本仓库维护。

## 实现与验证

以具体使用场景推进，避免为尚未出现的需求建立大规模抽象。明确原型是回答问题的试验还是准备保留的实现。

为 class 和公开 method 编写适当的 docstring，说明其职责、表达的抽象，以及调用者需要理解的输入、输出和相互关系。必要时补充状态变化、副作用和错误行为。不解释内部实现细节，也不机械重复名称和类型签名已经清楚表达的信息。公开函数遵循相同原则。

实现时，明确标出承担输入校验的函数和代码段，统一使用 `# Input validation: <校验内容>` 注释。

专用于输入校验的函数，在定义前标注；校验逻辑与其他处理混合的函数，在实际校验代码块前标注。说明检查的约束或拒绝的输入，例如类型、数值范围、必需字段、引用有效性或结构一致性，不只写“检查输入”。

按连续校验块标注，不要求每个条件重复添加；普通计算、数据转换和内部不变量检查不混标为输入校验。新增或修改输入校验逻辑时，同步维护标记。

对变更运行适当检查，测试预期应来自需求、独立算例或其他可信依据，不照抄被测实现。不存在或未运行的检查必须如实说明。必要时沿实际代码的数据流解释关键选择，帮助用户理解修改位置和代价。

编写或修改测试前，先简要明确测试目的：要验证哪项需求或契约、希望发现哪类错误、预期结果依据什么，以及通过后能说明什么、不能说明什么。相关测试可以按组说明，不要求逐条套用模板。先明确目的，再编写测试；不能事后用已有测试反推目的，也不能只复刻被测实现。

测试目的可先在交流中说明，并在实施记录中简要保留。已有授权范围内的测试不因此新增审批步骤；发现需求或契约歧义时，再返回讨论。

## Git 与交接

遵循 [Git 工作方式与提交信息](docs/git-workflow.md)：以 `main` 为长期主线，每次尝试从当时的 `main` 建立独立主题分支，成果整理后再集成。后续新尝试从更新后的主线出发。

所有 commit message 使用英文。探索提交以清楚记录为主；主线提交遵循文档中的标题、正文和逻辑完整性约定。

当累积改动已经构成一次逻辑完整、可审阅的提交时，agent 可以主动建议提交并说明范围，避免大量改动积累后才提交；建议不等于获得授权。

提交前检查差异和暂存范围，只提交本次授权的文件。提交、集成、推送和共享历史修改分别按授权范围执行，不覆盖无关工作。

并行修改时按需要隔离工作目录和产物位置，不为每个小任务强制创建 worktree 或 PR。结束时说明修改内容、验证结果和未决事项。

# 架构与实现分离的协作约定

## 目标

保持整体架构清晰、可控、方便理解。通过限制实现任务对其他模块内部细节的依赖，检验模块划分和契约是否足以支持独立实现。

局部实现不要求一次达到最优，但必须如实报告缺陷和验证结果，不得以破坏架构边界的方式掩盖问题。

## 架构决策与自主权限

架构关注模块职责、边界、依赖关系、数据与状态归属、对外契约，以及已确认的全局约束。

仅服务于局部、可在不影响上述事项的情况下替换的类、函数、算法和内部组织，由实现 Agent 自主决定。

只有能够明确判断调整不影响整体架构时，Agent 才可自主进行。涉及架构变化，或影响尚不确定时，必须先与用户讨论，得到确认后再做相关修改。

不得为了完成局部任务，擅自改变公共契约、增加跨模块依赖、转移状态归属或绕过既定边界。用户已明确授权的事项不重复请求确认。

## 从设计进入实现

实现前，应明确本次工作的：

- 目标与验收条件；
- 负责的模块及允许修改的范围；
- 相关架构约束；
- 依赖模块的公开契约及其入口。

契约应足以让调用者理解输入、输出和相关行为，包括必要的错误、副作用、时序及一致性保证。按实际需要说明，不机械补齐无关条目。

不要求预先设计全部内部类和函数。尚未明确且会影响架构的事项留在设计讨论中，不能交给实现阶段默默决定。

每次实现开始时，简要说明本次范围。范围已明确且已获授权时直接推进；不自行扩大范围以获得更多实现信息。

## 实现任务的阅读边界

实现 Agent 可以读取：

- 本任务涉及的架构决定和公共约定；
- 当前负责模块的实现、内部测试和必要的构建配置；
- 依赖模块的公开声明、契约文档及明确面向调用者的使用示例、契约测试。

禁止读取任务范围外模块的内部实现、内部测试及描述其内部设计的材料。不能通过终端、搜索、Git 历史、记忆、反编译或其他 Agent 的转述绕过该限制。

此限制关注信息是否进入实现 Agent 的上下文；语言服务器索引或测试执行依赖代码，本身不视为阅读实现。

实现任务宜使用独立上下文。交接时不携带依赖模块的内部实现摘要。若当前上下文已经包含相关实现，说明情况，不声称本次是仅依赖契约完成的实验。

## Serena 使用约定

优先使用 Serena 定位和读取相关符号，并尽量限定查询路径和范围，避免先阅读整个仓库。

读取自身实现时，可以获取符号正文。查询依赖时，只定位公开声明并获取必要的签名和契约信息；支持相应参数时使用 `include_body=false`，按需获取文档信息。

符号名称或概览不等于完整契约。信息不足时查阅公开契约文档，不据此猜测行为，也不展开实现补足。

引用查询、文本搜索、跳转和诊断工具可能返回其他模块的代码片段。调用前考虑返回范围；无法限定时，不在受限实现任务中进行全局探索。

声明与实现混在同一文件时，优先精确获取公开声明。工具无法分离时报告限制，不直接读取整个文件。

Serena 不可用或返回信息不足时，可以在相同阅读边界内使用其他工具，并记录影响实验的工具问题。

## 契约缺口与异常处理

无法仅凭契约继续时，报告：

- 正在完成什么；
- 缺少哪项行为保证或发现什么矛盾；
- 为什么该信息影响当前实现；
- 建议补充或调整什么。

局部实现选择自行解决；契约或架构问题先与用户讨论。等待期间可继续不受影响的工作，不擅自扩大阅读范围。

测试失败不自动授权跨模块阅读。先检查自身实现与契约；如确需跨模块诊断，说明原因和所需范围，由用户确认。

意外看到范围外实现时，停止进一步展开，记录来源、范围及可能影响，不隐瞒，也不宣称能忘掉已读内容。能否继续作为受限实现实验，需要如实说明。

## 验证与记录

按契约验证可观察行为，并运行与改动相关的测试和集成检查。可以执行真实依赖，但不借测试过程主动提取其源码。

不得通过削弱契约、删除有效测试或让调用者适配内部缺陷来制造通过结果。发现契约本身有问题时，返回讨论。

实施过程中维护简短的阅读记录，注明实际读取的文件、章节或符号范围、外部资料及用途，并区分实现阶段与测试阶段。已有上下文、其他 agent 提供的信息，以及搜索或工具输出中意外进入上下文的范围外内容，也应如实说明。不逐条抄写工具调用，不将 agent 自述视为独立证明。

分别记录实现与测试的用时。实现包括相关阅读、分析、代码编写及实现修正；测试包括测试目的梳理、测试编写、执行及测试代码修正。二者交替进行时按实际活动累计，不把测试发现后的实现修正全部算作测试用时。注明计时方式和范围；等待用户或任务暂停的时间单列，无法可靠区分时说明限制，不补造精确数字。

工具提供 token 用量时，记录其来源和统计范围，并在可取得时区分输入、输出及实现、测试阶段。只有整体统计时仅报告整体值；无法取得时明确写“不可用”，不根据文本长度或账户额度变化反推消耗。

上述信息在实施记录中汇总，连同测试目的、实际结果和局限一起保留。

每个任务结束时，在项目约定的位置简短记录：

- 完成内容及验证结果；
- 契约是否足够，实际出现过哪些缺口；
- 哪些事项返回了架构讨论；
- 是否发生越界、已知上下文混入或工具限制；
- 尚未解决的问题和有价值的局部不足。

记录以实际过程为依据。区分 Agent 自述与工具记录，不把“未发现越界”写成“已证明没有越界”。不逐条抄写工具调用，也不为满足格式编造问题。
