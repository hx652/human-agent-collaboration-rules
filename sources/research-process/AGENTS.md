# 协作与记录约定

## 目标

支持长期探索和跨 session、跨项目协作，
同时保留思考与行动的过程，而不只有最终结果。
科研是初始场景，未来可以用于其他领域。

## 开始工作

先读取 overview.md、state.md、projects/README.md。
根据任务查阅关联材料，不默认加载全部历史。
明确当前环境及文件访问范围，不将云端工作区视作用户本地电脑。
用户未确认执行过命令时，不假设目录、仓库或配置已经存在。
无法访问材料时明确说明，不假装已经同步。
继续旧任务或遇到状态冲突时重新读取相关文件。

## 长期记录更新

先讨论，再给出候选更新，列出拟修改文件、具体内容和理由。
用户审阅、提出意见并确认后，才能写入。
本次批准只覆盖本次确认的内容，不是永久写入授权。
具体代码任务的执行范围按该任务的授权确定。

区分用户报告、实际验证的事实、假设、决定和未决问题。
不将猜测写成结论，不将计划写成已经完成。
不替用户扩大研究目标或补充未经确认的主张。
保留用户原意、不确定性和重要个人表述的背景。

## 内容组织

overview.md：当前整体理解与原则。
state.md：整体阶段、重点、阻碍和下一步。
projects/README.md：项目索引与关联。
projects/<project>/README.md：项目上下文及材料入口。
journal/：讨论、尝试、选择理由、理解变化和复盘。
inbox/：没有明确归属的零散想法，不强迫转化为任务。
experiments/：实验问题、设置、结果、解释及局限。
references/：文献来源、阅读笔记与个人理解。
assets/：供笔记引用的小型附件与自制插图，按主题分组。

已有明确项目归属的想法可以放在该项目目录，并注明成熟程度。
项目实现文档优先链接原仓库，避免重复维护。
旧结论变化时保留原始过程，增加修正原因和新记录链接。
引用实验结果时尽量注明代码版本、数据、配置和产物位置。
不要求每轮对话存档，也不能只保留最终结果。

## 配套资源管理

小型插图、截图和必要附件放在 assets/，使用稳定名称和库内相对链接。
一组需要长期维护的资源放在同一主题目录，简短说明用途、来源、关联笔记、
修改入口、生成方式和重要限制；程序生成的图同时保留绘图源文件及必要的小型输入。
正式项目代码继续留在原代码仓库，不在此重复维护。

普通修正沿用文件名，提交 Git 后由历史保留版本；有必要对照的不同方案才另存文件。
PNG、ZIP 等可再生成的导出副本按需保留；assets/ 下的 exports/ 目录不进入 Git。
不按扩展名统一排除图片或 PDF，以免丢失实际需要的附件。
原始数据集、长视频、模型权重和大批日志留在外部目录，笔记注明资源名称、版本及位置，
设备专属路径继续写入 local-paths.md。记录路径不等于已同步文件。
不要将临时目录或会话输出目录作为长期笔记的唯一资源位置。
附件归档及嵌入仍遵循本次讨论、审阅和确认的写入约定。

## 维护与沟通

在交流与记录中，AI 协作者自称及被指称为“agent”，不使用“助手”；该约定适用于后续 session。

用户提出想法后，agent 应独立审阅和判断，说明赞同、保留或反对的理由，不直接顺着用户的意见作出结论。
不急于收敛方案；存在多种合理方案或缺少必要信息时，继续讨论，明确备选方案、权衡和未决问题，不将尚未讨论清楚的建议当作已确认决定。

保持简洁，按实际使用问题逐步完善流程。
生成的方案应明确但简洁，不要过于冗长，也不要过度发散下一步的行为。
命令可以按语义分节解释，但最终提供一份完整可复制版本，
避免用户逐段复制。
写入后准确说明修改了哪些文件及尚未完成的事项。
Git 提交前检查差异，只提交本次确认的文件。
不自动推送远程，不修改无关变更。
